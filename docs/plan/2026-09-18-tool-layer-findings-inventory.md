# 工具层：2026-09-18 一天挖出的全部问题（清单 + 我的判断）

> 状态：现行 · 2026-09-18
> **这份文件只做一件事：把散在六条分支、两份结构评审和一次真机 23 轮里的工具层发现，收在一处。**
> 它是**输入**，不是结论——「我们的分层对不对」那一问要拿它去和别人的设计对照才能回答（见 §5）。

## 1. 起点：用户看到的那一件事

用户点「新建方案」让 Agent 照文稿出分镜。main 上 5 轮真模型：**0 轮出东西**，
4 轮模型根本没调工具、只回了一段文字，1 轮调了 `draft_shots` 连挂 3 次。

## 2. 全部发现（14 条，按「模型有没有可能做对」分组）

### A · 模型**不可能**做对的（宿主要了它拿不到的东西）

| # | 问题 | 后果 |
|---|---|---|
| A1 | 多镜 `draft_shots` 要求模型自己填整只 `candidate`（`candidateId`/`providerId`/传输层接线）| 分镜天生多镜 → **这条路 100% 失败**。单镜路早就修过同一个毛病并写下了理由（「让模型不必去发明内部 candidate ID 和供应商接线，之前的行为表现为一次假拒绝」），只修了 N=1 那个 arity |
| A2 | 参考图要求 `contentHash` + `version`，而**没有任何读工具返回 `contentHash`** | Agent 挂的参考图**一张都递不进去**。真机 27 次失败里 11 次是它 |

### B · 模型做对了，被我们弄丢或拒掉的

| # | 问题 | 后果 |
|---|---|---|
| B1 | 动词声明了每镜 `title`，宿主 `shots[]` 是 `.strict()` 不认 | 整次调用被拒。模型填的是**我们说明书上的字段** |
| B2 | `title` 从动词到两个终点（画布节点标签、花钱确认卡）中途被**五处手写的逐字段重建各丢一次** | 每个节点叫「镜头 shot-1」，花钱卡上是被砍断的提示词前 120 字。编译期全合法、测试全绿 |
| B3 | 翻译层把每镜与顶层的 `candidate.providerId/modelId` **整个丢掉** | 模型说「用 apimart 的 image-1」，宿主拿用户默认模型去花钱，**没有任何人报错** |
| B4 | `shotId` 在没有 `draftId` 时被剥掉 | 模型以为改了第 3 镜，实际新建了一份草稿 |
| B5 | `read_script` 的 `scope`：内部 lane 手写 `?? "full"` 兜住，外部 MCP 面没有这行 | 外部宿主上 `nomi_document_read` 直接失败 |

### C · 我们凭空造出来、然后指责模型的

| # | 问题 | 后果 |
|---|---|---|
| C1 | `read_timeline` / `look_at_media`：翻译层从半开区间凭空造 `endFrame: 0` | 宿主回「Number must be greater than 0」——**指责一个模型从没写过的字段** |
| C2 | `look_at_media` / `arrange_canvas` 互斥参数集被同时接受，一个静默忽略；`arrange_canvas` 无参从翻译层抛裸 `Error` | 模型收到一个它看不懂的拒绝 |

### D · 我们自己两处打架

| # | 问题 | 后果 |
|---|---|---|
| D1 | 技能 `:202` 让调 `draft_shots`，`:203` 说「绝不调用写画布/生成类工具」——而它正是写画布的 | **5 轮里 4 轮不调工具**。`:203` 是 2026-06-13 给当时只读的 `propose_storyboard_plan` 写的，换工具时没删 |
| D2 | 技能写「`durationSec` 一律填 `0`」，动词是 `z.number().positive()` | 真机 5 次 ajv 失败全是它。模型自己说破了：「上次按图片分镜规范填了静帧时长，系统不接收」 |
| D3 | 技能写「`draft_shots` 不碰画布」——**写下去那天就是假的**（动词自述「在画布上创建或更新草稿镜头」）| 漂移早已发生、活了一段时间、**没有任何人或机器发现过** |
| D4 | 「整份计划不能只有锚」的约束只住在宿主 | 模型做标准分镜流程（先立视觉锚再排镜头，**正是我们自己的导演技能教的**）被拒。27 次失败里 11 次 |

### E · 结构性的

| # | 问题 |
|---|---|
| E1 | `generationTransportAdapters` 里手抄了一份方法别名的输入形状，**比真契约窄**：手抄 5 个键，真契约 14 个，少掉的 9 个正是模型最常写的（模型/模式/参数/参考图）。今天没爆只因暂时没路由到那几支 |
| E2 | 两个失败出口，一个带「认出裸码就丢掉」的判断、兄弟出口没有。文档/画布/时间轴三条 lane 走没有的那个 |
| E3 | `laneVerbTransport` 的 `modelSetup` 分支是死代码 |

## 3. 我从这 14 条里读出的形状

**一个能力被重复表述四遍**——动词声明、翻译层、契约 schema、handler 及下游投影。
四遍都是手写的，中间没有任何东西比对。

- A 类 = 宿主那一遍要了模型那一遍给不出的东西
- B/C 类 = 翻译那一遍是手写的
- E1/E2 = 同一件事在两处各写一份，其中一份更窄 / 少一道判断
- D 类 = 技能又复述了一遍（第五遍）

**为什么缺陷全堆在内部这一面**：外部 MCP 面早就有一道对应的门岗
（`check-mcp-operation-constructible`），内部动词面**一道都没有**。

## 5. 没做的那一问（本文件交出去要回答的）

**「该有两遍，不该有四遍」这个判断，是从我们自己代码里推出来的，没跟任何人对照过。**

它可能对，也可能是在给现状找理由。要回答的是：

1. 顶尖产品在「模型看到的工具面」与「宿主的准入契约」之间**分几层**？各自为什么？
2. 我们说「关卡不能拆」（跨进程 + 花钱闸），别人有没有同样的约束、他们怎么处理？
3. 「翻译从对应关系派生」这条路，别人做没做、代价是什么、有没有更好的解？
4. 我们已经落地的那批（§4）里，有哪些是**对的方向走错了实现**？

**允许推翻 §3 的判断**——如果对照下来我们的分层本身就错了，那 §4 里一半的工作是在错的地基上加固，
早知道比晚知道便宜。
