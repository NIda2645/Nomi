# P1→P3 MCP 可编辑单镜生成阶段证据

日期：2026-08-23  
分支：`codex/p0-runtime-foundation-20260822`  
范围：P1/P2 边界、P3 零 provider-quota seam、真实 MCP/GUI 走查，以及一次受控的 APIMart 低规格图片 transport smoke。

## 用户价值结论

- P1 解决“换模型/供应商/输入模式就要学习一套 Nomi 私有格式”的摩擦：模块、provider、model、mode、参数和素材都是声明数据；不支持时在 provider 前明确失败。
- P2 解决“我只是改了一个参数/换了参考图，却不知道系统实际提交了什么”的摩擦：candidate 每次编辑都生成新 revision/hash；字段被丢弃时有 warning/ledger；封存后编辑返回 `new_draft_required`，不会偷偷改原任务。
- P3 seam 解决“要离开 MCP 去 Nomi 点第二次、崩溃后怕重复扣费”的摩擦：provider-neutral adapter 只接受 sealed contract；envelope 先落盘；provider 已接受但回执丢失时只进入 reconcile，不盲重提。

## 用户体验验收原则

- MCP 客户端优先：客户端能提供主进程可验证的 attestation 时，用户在当前客户端点一次即可由主进程签发 receipt；没有可验证证明时只回退到同一个 challenge 的一张 Nomi 卡，避免双重审批。
- 可编辑和通用：模型、供应商、image/video/audio 模式、参数和参考素材均是 candidate 数据，不写死在 dispatcher；所有编辑都在封存前发生，封存后通过新草稿保护旧合同。
- 简洁可见：用户只看到决定所需的摘要和一个 primary action；进行中用文字+图标+进度，错误写明事实与唯一下一步；内部状态名不直接甩给用户。
- 真实场景：后续 journey 必须覆盖自由换模型/供应商/模式/参数/参考素材，以及取消、重启、断线、回执丢失和 provider 能力缺失，而非只覆盖固定 fixture 的 happy path。

## APIMart 受控 smoke（2026-08-23）

- 凭证通过 Nomi 的模型目录写入本机安全存储；没有写入代码、日志或提交，也没有在输出中回显明文。
- 只跑一张 `Seedream 5.0 Pro`：`text-to-image`、`1:1`、`1K`、`n=1`；没有视频或高分辨率请求。
- `POST /v1/images/generations` 返回 HTTP 200 和 `data[0].task_id`；`GET /v1/tasks/{task_id}` 从 `pending` 到 `completed`；结果为 1024×1024 JPEG，结果地址 HTTP 200。
- 这证明凭证、模型参数和 APIMart 的异步查询传输可用，但**不证明 P3 可安全自动重试**：官方文档只明确提交与 task 查询，没有给出原生 idempotency key 或取消接口。按照既定 fail-closed 方案，APIMart 目前只能作为 transport 已验证、P3 capability gate 仍阻塞的 provider。
- 为了让实测使用与产品网络出口一致，修正了 transport spike 漏传 Electron `session.defaultSession` 的测试入口；该修复不触碰生产生成路径。

## 唯一决策门

P3 零额度 semantic journey、真实 MCP/GUI 共享确认走查、打包 smoke、全门和一次 APIMart 1K transport smoke 均已通过。现在只剩一个产品/供应商能力决策：

1. 继续坚持严格 capability gate：APIMart 保持“可配置、可预览、可做 transport smoke”，但不能从 P3 自动提交；换用能公开证明原生幂等、查询/核账和取消能力的 provider，或等待 APIMart 补齐证明。
2. 若允许 APIMart 进入付费 P3，则必须接受未知结果只能人工核账、不能安全自动重试，且取消只能显示“无法确认远端取消”的降级体验；这会改变当前的安全承诺，不建议默认开启。

默认建议仍是 1：严格阻塞缺少 native submit idempotency/query/reconcile/cancel 的 provider；`submission_unknown` 只核账不盲重提。
