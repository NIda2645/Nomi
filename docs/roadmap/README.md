# docs/roadmap —— 后续迭代的核心资料

> 状态：📎 长期文档 — 这一套是「**接下来做什么，以及为什么**」的家。
> 建于 2026-09-14，起因是用户一句话：把散在微信备忘、没落地的设计、和刚聊完的方案，**沉淀成一份能对照着干活的东西**。

## 三份文件，各管一件事

| 文件 | 它回答什么 | 什么时候改它 |
|---|---|---|
| [`TODO.md`](TODO.md) | **接下来做什么** —— 唯一的待办真相源，分十组，每条一个稳定 ID | 状态变了就改（开工 → `doing`，合了 → `done` + PR 号）。**只改这一份**，别在别处再开一张清单 |
| [`designs-not-yet-built.md`](designs-not-yet-built.md) | **设计到底落地没有** —— 逐面实扫的对账表，带 `file:line` 和基准 SHA | 重新实扫之后（改的时候把基准 SHA 和日期一起改） |
| [`sources/`](sources/) | **原话和原始证据** —— 用户的原始备忘、截图、当时的调研报告 | **基本不改**。它是原料，不是结论；新原料按日期加新文件 |

## 怎么用（三步）

1. **派工 / 出方案 / 开分支之前，先翻 `TODO.md`。** 要做的事在不在表里？在，就按那条的「下一步」走；不在，先想清楚它为什么不在——很可能是**故意没收**（见 TODO 末尾那一节），也可能是真漏了。
2. **对某条有疑问**（写得含糊、觉得判错了、不知道用户当时到底想要什么）→ **回查它「来源」那一列**。链接指向 `sources/` 里的原话或截图，或者 `docs/design/` 里的设计正本。**别靠记忆重新解释一遍用户想要什么。**
3. **做完改状态。** 合进 main 才写 `done` 并带上 PR 号（R11 的口径：进了远端目标分支才算「已解决」，侧分支只能叫「已实现」）。

## 三条维护纪律

- **ID 不回收。** 做完了改状态，不要删行。删了，下次又会有人把同一件事重新「发现」一遍——这份表最大的价值就是让同一个问题只被发现一次。
- **每条都要指得出来源。** 写不出来源的条目，说明它是我自己想做的事，不是用户要的——先去问，别先进表。
- **快照文档要写日期和基准 SHA。** `designs-not-yet-built.md` 和 `sources/` 里的 digest 都是**某一天的快照**，会过期；它们和 `TODO.md` 打架时，以 `TODO.md` 为准，然后重新实扫。
  （09-08 那份设计账本就是反例：它把三项已经落地的记成「未落地」，因为中间合了几波 PR 没人回来改。）

## 和别处的关系

- **`CLAUDE.md`** 是工程纪律（怎么干活），**这里**是工作内容（干什么）。CLAUDE.md 里只有一行指向这份 TODO。
- **`docs/plan/`** 放单件事的完整方案（范围 / 不动项 / 回滚 / 验收门）。TODO 里的大件只留一行指针，细节留在 plan 里——抄过来必漂。
- **`docs/lessons/`** 放踩过的坑（同一个坑怎么不再踩）。一次性排障记录归那边，不进 TODO。
- **`docs/design/`** 放设计正本。`designs-not-yet-built.md` 只做对账，不复制设计内容。
